## ③【v1.2.15】联播起点：从橙色指针处开始

### 皓哥要的逻辑（原话，已确认）
- 指针在**绿区** → 从**指针处**开始播
- 指针在**红区** → 跳到**下一个绿区**开头开始播

### 真凶：原片时间 / 成品时间单位错配
`BKEditorViewController.swift:1096` 传 `lastTime`（**原片时间**）进 `startKeptTime`，
该函数返回的也是**原片时间**，但 `1104` 行**直接拿它当成品时间**去 `seek`：

```swift
guard let startOut = BKJointBuilder.startKeptTime(for: lastTime, keeps: keeps) else { ... }
jp.seek(to: CMTime(seconds: startOut, preferredTimescale: 600), ...)   // ← 单位错配
```

实测（IMG_4580 真实段边界）：指针在源 `1.745s`（绿区2 内部）→ 正确成品位置 `0.415s`，
实际 seek 到 `1.745s`，**错位 1330ms**。`Joint.outputTime(at:)` 换算函数**已存在但从未被调用**。

### 附带问题
`startKeptTime` 循环条件 `b > t + 0.001` 不对——指针正好落在绿区**结束边界**上会被判成红区而跳走。
`tools/diag_jointstart.py` 复刻 9 个测试点，**错 3 处**（结束边界上、末尾之后、结束前 0.5ms）。

### 改动清单
- [ ] `BKJointBuilder.startKeptTime` 重写判定顺序
  - 先判「t 是否落在某绿区内（`a-1e-9 <= t <= b+1e-9`）」→ 是则**返回 t**
  - 否则往后找第一个 `a > t` 的绿区 → 返回 `a`
  - 末尾之后返回最后一个绿区的 `b`（**不再返回 nil**，避免「指针后面没有绿区了」误报）
  - 容差统一用 `1e-9`（替掉现在的 `0.001`）
- [ ] `jointTapped()`：`startOut` 求出的是**原片**时间 → 改用 `built.outputTime(at: startOut)` 换成**成品**时间再 `seek`
- [ ] `syncPlayhead` 那行保持传**原片时间**（它本来就该驱动原片轨道，别一起改错）
- [ ] 日志补一条起播信息（原片起点 / 成品起点 / 段序号），方便真机核对

### 验收
- [ ] 指针在绿区中间 → 从指针处播（不是从绿区开头）
- [ ] 指针在红区 → 跳到下一个绿区开头
- [ ] 指针在绿区结束边界上 → **就地播**（不再跳走）
- [ ] 指针在最后绿区之后 → 不再提示「指针后面没有绿区了」

### 风险
低。纯计算改动，不碰导出规格、不碰 UI 布局。

## ①【v1.2.16】导出音画错位：画面比声音滞后

### 已排除源素材（ffmpeg 实测四条样片）
- 音视频 pts 起点都是 0，网格规整（视频 16.67ms/帧 @59.96fps、音频 21.33ms/块 @48kHz）
- 参照组 `samples/IMG_4580_去气口.mp4`（ffmpeg 剪的）**音画完美对齐**（视频末帧 11.574+帧长 ≈ 音频末帧 11.605）
- → **源片没问题，是导出重排的锅**

### 元凶一（主因）：`expectsMediaDataInRealTime` 单边设置
`BKExporter.swift:299` —— `504f473`（IMG_4873 死锁案）加的兜底，**只设在 videoInput，audioInput 没设**。

```swift
videoInput.expectsMediaDataInRealTime = true   // ← 音频侧没有
```

实时模式下 AVFoundation 不保证按 append 顺序交织、会自行重排时间戳追实时 →
视频按实时流缓冲、音频按离线精确写入，**两轨策略不一致** = 画面滞后于声音。还会悄悄丢帧。

### 元凶二（叠加）：段末尾量化缺口逐段累积
`inRange` 按 `[segStart, segEnd)` 放行，但 `outputCursor` 按**标称** `segEnd - segStart` 推进。
段末尾「不足一帧 / 不足一音频块」的尾巴在视频轨和音频轨上长度不同，且**永不归零**。

实测末段累计错位（`tools/diag_avsync.py`）：4580 `−6.1ms` / 4582 `−5.1ms` / 4583 `−14.6ms` / 4990 见脚本。
单看这一项人耳不敏感，**与元凶一叠加才变成可感知的错位**。

### 改动清单
- [ ] **删掉** `videoInput.expectsMediaDataInRealTime = true`（第 299 行）+ 上方那两行注释重新说明
      （`inRange` 已经治住 IMG_4873 的真根因——越界样本导致时间戳倒退——这行是当时的权宜之计）
- [ ] `drainSegment` 增加一个 `lastWrittenEnd` 出参，返回**本段实际写入的最后一个样本结束时间**
      （视频 = 末帧 PTS + 帧时长；音频 = 末块 PTS + 块时长，取两轨较大值作为该段真实长度）
- [ ] `exportSync` 的 `outputCursor` 改为按**实际写入长度**推进，替代标称 `segRange.duration`
- [ ] **保留** `inRange` 过滤（它是对的，删了会退回 IMG_4873 死锁）
- [ ] `BKDiag` 诊断报告加一项：每段「标称长 / 视频实长 / 音频实长 / 差值」

### 验收（⚠️ CI 验不出来，必须真机）
- [ ] 真机导出一条多段的成品 → 把文件发我 → 用 ffmpeg 量成品视频末帧 vs 音频末帧的 pts 差
- [ ] 或者你自己在剪映里对着画面拍手/打板子听音画是否对齐
- [ ] 确认没退化：多段拼接**不再死锁**（IMG_4873 场景）

### 风险
**中高**。去掉实时标志后，IMG_4873 那种「多段拼接卡死」有复发可能。
所以必须配套：`inRange` 保留 + 真实 writer 错误照常抛出 + 兜底超时仍保留。
**第一版建议只做这一处改动就发版**，观察真机是否还死锁，再叠加元凶二的修复。

## ②【v1.2.17】放大轨道后拖接缝条卡顿

### 根因：`draw(_:)` 忽略脏矩形，每帧全量重画
`BKTrackView.swift:399` `TrackCanvas.draw(_ rect:)` —— 系统传进来的 `rect` **完全没用**。

实测（390pt 宽）：

| 缩放 | 每帧柱数 | 屏幕可见 | 白画比例 |
|---|---|---|---|
| 6 屏 | 2340 | ~390 | 83% |
| **20 屏** | **7800** | ~390 | **95%** |

每根柱还额外查一次 `env.peak(from:to:)`。拖动时链路
`onPan` → `didDragBoundaryNear` → `applyMarks` → `BKTimeline.normalize` + `commit` → `setNeedsDisplay`
= 60fps 下**每秒 60 次全量重算 + 全量重画**。

### 改动清单（建议三条一起做，第 1 条性价比最高）
- [ ] **`draw(_ rect:)` 用 `rect` 裁剪**：只遍历可见列
      `let c0 = max(0, Int(rect.minX - pad))`，`let c1 = min(cols, Int(rect.maxX - pad))`
- [ ] **拖动中降采样**：`boundaryDragging == true` 时每 2~3px 画一根柱，松手后 `setNeedsDisplay()` 画全精度
      （`BKEditorViewController` 的 `boundaryDragging` 已有，拖动结束会置回 false，链路现成）
- [ ] **波形层缓存**：把波形柱预渲染成离屏图 / `CALayer`，
      拖动时只重画会动的粉红覆盖层 + 把手，不重画柱状图

### 验收（⚠️ CI 验不出来）
- [ ] 20 屏下拖接缝条，全程跟手无卡顿
- [ ] 松手后波形全精度恢复（不能因为降采样留下糊的波形）
- [ ] 滚动、捏合缩放、点段切换红绿**都不能因为这次优化而变样**（最容易出回归的地方）

### 风险
中。`draw` 改裁剪要小心坐标系（`rect` 是 canvas 局部坐标，要减 `pad`），
缓存方案要处理 `setContent` 换素材时失效。**建议第 1 条先发**（改动最小、收益最大），2、3 观察后再决定。

## 复盘要点（写给下一个版本的自己）

1. **「先量数据再改代码」今天又救了一次**：① 源素材用 ffmpeg 量过 pts 起点，才排除了「采集端错位」这个方向；
   ③ 用真实段边界复刻出 1330ms 错位，才看清是单位错配而不是逻辑写错。
2. **加性能/同步类标志前先查官方语义**：`expectsMediaDataInRealTime` 是为「实时采集」设计的，
   拿它给离线导出兜底属于误用——当时为了绕死锁加的，两周后就成了新 bug 的元凶。
3. **换算函数写了不调用等于没写**：`Joint.outputTime(at:)` 一直在，缺的就是那一次调用。
4. **`draw(_:)` 的 `rect` 参数不要浪费**：全量重画在小图上没事，放大 3 倍后就变成 95% 无用功。
5. ⚠️ **本机无 Swift 编译器，同步类和性能类问题 CI 都验不出来**。分批发版、真机复核，别混在一起。
