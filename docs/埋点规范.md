# 埋点规范（完整开发文档 · 第 01 章）

**这份规范存在的唯一原因：你没有 Mac，看不见 Xcode 控制台。**

App 在自己的手机上跑，出问题的时候你手里只有黑盒。日志是唯一的线索来源。写得好，一个日志文件就能定位问题；写得随意，等于没写。

配套实现：`bk-clip/app/DebugConsole.swift`

## 一、六个必打点

### 1. 视频导入后 —— 记真实显示比例

```swift
guard let track = asset.tracks(withMediaType: .video).first else { return }
let natural = track.naturalSize
let real    = natural.applying(track.preferredTransform)
let seconds = asset.duration.seconds

BKLog.shared.i("""
导入素材 \(seconds)s | 原始 \(natural.width)×\(natural.height) \
旋转后 \(abs(real.width))×\(abs(real.height)) | 朝向 \(isPortrait ? "竖" : "横") \
预估码率 \(Int(track.estimatedDataRate / 1000))kbps
""")
```

**为什么必记：** naturalSize 会把竖屏素材报成横屏（iPhone 拍的 mov 带旋转 metadata）。一旦比例算错，后面预览区变形、导出黑边全都跟着错。日志里一看就知道是原始值错还是 `preferredTransform` 没应用。

### 2. 波形提取 —— 记耗时

```swift
BKLog.measure("提取波形") {
    envelope = extractEnvelope(from: asset)
}
```

**为什么必记：** 输出 `⏱ 提取波形 耗时 3800ms`。这是整个 App 最重的一步。3 秒以上的素材如果超过 5 秒，就该考虑降采样精度或做后台线程了 —— 而这个判断只能靠耗时数据，靠感觉是感觉不出来的。

### 3. 自动检测气口 —— 记算法中间值

```swift
BKLog.shared.i("气口阈值 \(threshold)dB（Otsu 原始 \(raw)dB）切成 \(segments.count) 段")
if raw != threshold {
    BKLog.shared.w("阈值被夹逼到安全区间 \(raw) → \(threshold)")
}
```

**为什么必记：** 自动检测是整个 App 的核心价值，而它出错时**表面上看不出来** —— 只是切出来的气口多了或少了。
日志里记下 **Otsu 算出的原始值**和**夹逼后的实际值**两个数字很关键：

- 两个值差得多 → 说明这批素材音量分布反常，经验区间可能不适合你
- 两个值一样但还是切不好 → 那是防碎参数（最短气口/最短片段）的问题，不是阈值

### 4. 导出 —— 记完整参数与结果

```swift
BKLog.shared.i("导出开始 目标 \(w)×\(h) fps \(fps) 码率 \(bitrate/1000)kbps 段数 \(kept.count)")
// ...
BKLog.shared.i("导出完成 耗时 \(ms)ms 体积 \(size)MB")
// 失败时
BKLog.shared.e("导出失败 \(error.localizedDescription)")
```

**为什么必记：** 「导出失败」这四个字没有价值。真正有用的是**失败时的分辨率和码率** —— 九成情况下是某个素材的某个参数组合触发了编码器限制。没记参数等于白记。

### 5. App 进后台 —— 记现场状态

```swift
NotificationCenter.default.addObserver(forName: UIApplication.didEnterBackgroundNotification,
                                       object: nil, queue: .main) { _ in
    if exportQueue.isRunning {
        BKLog.shared.w("切后台时正在导出，已完成 \(exportQueue.finishedCount)/\(exportQueue.total)")
    }
}
```

**为什么必记：** iOS 会在 App 切走后不久挂起它，导出可能断在某一条上。记下「断了的时候已经完成几条」，就能确认 BackgroundTasks 有没有生效、断点续导该从哪开始。**这类问题不复现第二遍**，日志丢了就只能从头再来一遍。

### 6. 内存警告 —— 必须打点

```swift
override func didReceiveMemoryWarning() {
    super.didReceiveMemoryWarning()
    BKLog.shared.e("内存警告 当前 \(BKProbe.memoryUsedMB())MB 活跃视频 \(current?.name ?? "无")")
}
```

**为什么必记：** 内存警告是 App 被系统杀掉前的最后通牒。收到一次不一定死，连续收到基本必死。配合当时的视频名，就能锁定是哪种素材、哪个环节吃内存。

## 二、级别怎么选

| 级别 | 什么时候用 | 例子 |
|---|---|---|
| `v` | 排查时才想看的细节 | 波形分块读取进度 |
| `d` | 正常流程的技术细节 |  seeks 完成、composition 构建完成 |
| `i` | **默认用它**。关键节点的结果 | 导入完成、切了 12 段、导出成功 |
| `w` | 不正常但能继续跑 | 阈值被夹逼、切后台时还在导出 |
| `e` | 这一步骤真的失败了 | 导出失败、相册写入失败、内存警告 |

判断标准就一句：**这条日志出现在你眼前时，你要不要采取行动？** 不用 → `i`；要看情况留意 → `w`；必须处理 → `e`。

## 三、两条禁令

**禁止在高频回调里打点。** 播放每个回调、波形每一帧绘制、手势每次 move —— 这些每秒能触发几十上百次。后果有两个：日志几秒钟刷满 3000 条缓冲，把真正有用的挤掉；磁盘 IO 反过来拖慢 App，测出来的性能是假的。

要统计这类数据就在外面聚合一次，比如手势结束时打一条 `缩放结束 最终比例 x.xx`。

**禁止记录隐私信息。** 不记完整文件路径（相册 URL 里带 UUID 和设备信息）、不记相册以外的任何用户数据、不记设备手机号或 IDFV。只记文件名和时间 succeededFailed 结果。

## 四、出问题时的三步排查

1. **先按 `E` 过滤** —— 有大概率直接看到失败原因
2. **再按 `W` 过滤** —— 看异常但没崩的地方，往往在 `E` 之前几分钟
3. **都找不到，看磁盘的体积与时间** —— App Support 下 `logs/bk.log` 里包含内存被清掉之前的所有记录，比面板里那 3000 条完整

面板上「导出」按钮出来的文件直接发给我，我能按行号定位。
