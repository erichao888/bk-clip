## 一、先定路线：精确重编码，不用关键帧吸附

导出有两条路，之前一直悬着没定，**这里拍板**：

| | A 精确重编码 | B 关键帧吸附（`-c copy`） |
|---|---|---|
| 原理 | 解码后按任意时间点重排列再编码 | 只在关键帧处切断，不重新编码 |
| 切点精度 | **任意帧，精确到 1/60 秒** | 必须落在关键帧上 |
| iPhone 素材的实际误差 | 0 | **2~5 秒**（H.264 GOP 常常很大） |
| 速度 | 慢（几分钟） | 极快（几秒） |
| 画质 | 有极轻微损失（CRF 18~20 肉眼不可见） | 无损 |

**结论：走 A。** 理由很直接 —— **这个 App 的全部价值就是"切得准"**，为了省几分钟 encode 时间而让切点飘 2 秒，等于自废武功。

这也是 Python 预演脚本采用的做法，两条素材的导出时长都与理论值精确吻合（14.78s 对 14.78s），路线已经验证过。

## 二、导出规格（写死，别让 AI 自由发挥）

| 项 | 值 | 理由 |
|---|---|---|
| 容器 | **MP4** | 剪映 / 相册 / 微信 兼容性最好 |
| 视频编码 | **H.264 / AVC** | HEVC 在部分安卓机和旧设备上打不开，兼容性优先于体积 |
| 画质控制 | **CRF 18 ~ 20**（two-pass 不必要） | 肉眼无损，比固定码率更聪明 |
| 关键帧间隔 | **1 秒** | 导出的片子将来还要进剪映二次剪辑，关键帧密才好拖动 |
| profile / level | High / 4.1 | 覆盖 iPhone 拍的 1080p60 |
| 像素格式 | **yuv420p** | 必须。10bit（yuv420p10le）很多播放器解不了 |
| 音频 | **AAC-LC 128~192 kbps / 48 kHz** | 与源一致即可，别降采样 |
| faststart | **必须开** | 不开的话，文件要整个下载完才能播 |
| 帧率 | **跟随源素材**（ iPhone 是 59.96） | 早期版本这里写死 30，白白损失一半流畅度，已修 |

**注意：不要在这里降分辨率。** 素材本身是 1080×1920，导出就保持 1080×1920。降分辨率看着是省了体积，但用户拿去发抖音还要再压一次，等于压两遍。

## 三、⚠ 方向处理（这是最容易出事的地方，已在真实素材上踩过）

**iPhone 拍的视频，存储永远是横的 1920×1080，靠文件里一条 `-90°` 旋转标记让播放器转过来。**真实显示是 1080×1920 竖版。

在 Python 侧的表现是：经过滤镜重新编码后，ffmpeg 会自动把像素转正（输出真的变成 1080×1920），**但那条旋转标记也跟着继承到输出端** → 播放器再转一次 90° → **成品横了**。

AVFoundation 侧是完全同构的坑，三条必须写死：

```swift
// 1. 取真实显示尺寸 —— 绝不能直接用 naturalSize（那是存储的 1920×1080 横）
let track = asset.tracks(withMediaType: .video).first!
let natural = track.naturalSize
let real    = natural.applying(track.preferredTransform)   // 1080×1920 竖版 ✅
// 注意 preferredTransform 含负分量，取绝对值
let outW = Int(abs(real.width))
let outH = Int(abs(real.height))

// 2. 输出设置用「真实显示尺寸」
let settings: [String: Any] = [
    AVVideoCodecKey: AVVideoCodecType.h264,
    AVVideoWidthKey:  outW,
    AVVideoHeightKey: outH,
    AVVideoCompressionPropertiesKey: [
        AVVideoAverageBitRateKey: bitrate,
        AVVideoProfileLevelKey: AVVideoProfileLevelH264HighAutoLevel,
        AVVideoMaxKeyFrameIntervalKey: Int(fps)      // 1 秒一个关键帧
    ]
]
let writerInput = AVAssetWriterInput(mediaType: .video, outputSettings: settings)

// 3. ⚠ 最关键一行：把旋转标记写回去，否则成品一定躺下
writerInput.transform = track.preferredTransform
```

**第 3 行漏了，就是「导出成品变成横版」的经典症状。**建议把它加进 Code Review 的固定检查项。

埋点里要永久记录 `preferredTransform` 算出的显示尺寸（第 01 章埋点规范的一部分）。将来一旦有人反馈「导出方向不对」，这条日志能立刻区分是**尺寸算错**还是**标记没写回去**。

## 四、接缝治理：三道防线，一个都不能少

"去掉气口"本质上就是把几段视频首尾相接。**接缝是这个 App 唯一会产生新瑕疵的地方**，处理不好会听到"啪"一声爆音。

| 防线 | 做法 | 为什么 |
|---|---|---|
| 1. 零点对齐 | 切点定好后，在 **±10ms** 内搜索振幅最接近 0 的采样点，用它当真正的切点 | 在波形非零处硬切，会产生阶跃 → 爆音 |
| 2. 交叉淡化 | 每个接缝 **15ms** 淡入淡出 | 兜住剩余的不连续 |
| 3. 单次合成 | 所有片段放进**同一个 composition** 一次性写出 | 分别编码再拼 = 编两次、退化两次 |

Swift 里淡化用 `AVAudioMix`，不要自己去改 PCM：

```swift
let audioMix = AVMutableAudioMix()
var params: [AVAudioMixInputParameters] = []

for seg in keptSegments {
    let p = AVMutableAudioMixInputParameters(track: audioTrack)
    // 头 15ms 淡入
    p.setVolumeRamp(fromStartVolume: 0, toEndVolume: 1,
                    timeRange: CMTimeRange(start: seg.start,
                                           duration: CMTime(value: 15, timescale: 1000)))
    // 尾 15ms 淡出
    p.setVolumeRamp(fromStartVolume: 1, toEndVolume: 0,
                    timeRange: CMTimeRange(start: seg.end - fadeTime,
                                           duration: fadeTime))
    params.append(p)
}
audioMix.inputParameters = params
```

> 这条 Python 版已经实现（`export_preview` 里的 `afade`），两条素材导出后接缝干净。
> Swift 版的数值保持一致：**15ms**。

## 五、整体流程

```
草稿 JSON → 取出 kept 片段 → 构建 AVMutableComposition
   → 逐段 insertTimeRange（源 asset，同一份）
   → 挂 audioMix（接缝淡化）
   → AVAssetWriter 写出
   → PHPhotoLibrary 保存到相册
   → 写一条「导出历史」记录
```

**要点：源 asset 全程只有一份。** 最忌讳的是为每段创建一个 `AVAsset`（或更糟的：为每个 AVAssetReader）—— 一个 1080p60 素材光解码缓冲就上百 MB，几个一起来必被系统按内存杀掉。

## 六、资源约束（视频 App 的死因排行榜第一位）

| 规则 | 说明 |
|---|---|
| **单活跃解码器** | 同一时刻只允许一个 AVAssetReader 在跑。清单列表预览用低分辨率缩略图，不要挂全分辨率解码器 |
| **批量导出串行** | 一个接一个导出，不并行。并行三个 4K 导出 = 必然 OOM |
| **BackgroundTasks** | 导出注册 bg task，用户切后台尽量不断；但要在 bg 回调里正确收尾 |
| **断点续导** | 记录已完成到第几段；被系统杀死后重开可以接着做，不用从头 |
| **失败隔离** | 某一条失败不影响队列里其余条目，失败原因写进日志并标记状态 |

导出进行中必须有一条埋点（第 01 章规定：App 进后台时打 `warn`）——这条日志将来是你判断"导出失败到底是被挂起还是编码器报错"的唯一依据。

## 七、命名与冲突

```
BK_20260924_IMG2981.mp4
BK_20260924_IMG2981_2.mp4      ← 同名冲突自动加序号
```

前缀 `bk_` / `BK_` 便于在相册里一眼认出是本机导出的。冲突检测在实际写入前做（相册里可能已有同名）。

## 八、失败处理（用户能看懂的话术）

| 情况 | UI 表现 |
|---|---|
| 源视频被删 | 「源视频已删除，无法导出」+ 跳到下一条 |
| 磁盘不足 | 导出**前**先估算体积并比对可用空间，不足则提前提示，而不是写一半失败 |
| 编码器报错 | 显示错误码 + 「把日志发我」，调试面板里能导出（第 01 章） |
| 被系统杀掉 | 重开时提示「上次导出未完成，是否继续」 |

**导出前预估体积**这一步别省：(时长 × 码率) 算出来，手机空间有限，写一半失败比不导出更让人火大。

---

## 九、批量导出与进度

- 队列处理期间 UI 显示 `正在导出 2/7`，**不要显示百分比**——多段编码的百分比是假的，用户看着忽快忽慢反而焦虑
- 每条完成即从相册可见（边导边出），不要等全部完成
- 全部完成后汇总一行：「已导出 7 条，共节省 1 分 23 秒」—— **这句最能体现价值**，一定要有
