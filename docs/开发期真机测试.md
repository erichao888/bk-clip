# 开发期真机测试手册

> 与 `release/首台iPhone试跑指南.md` 的区别：
> 那份讲「第一次怎么装上去」（一次性），这份讲**写代码的那些日子里，每一轮改动怎么验**（每天重复）。
> **这份手册要在动手写代码之前看** —— 因为下面很多要求会影响代码怎么写（比如要在 UI 里留调参开关、要把关键信息打进日志）。

---

## 一、核心原则：真机测试是稀缺资源

没 Mac，意味着每验证一次改动，成本是：

```
改代码 → git push → 云构建 → 传 ipa → 手机 Safari 点链接 → 覆盖安装 → 手动操作
                     └──────────── 约 5 分钟 ────────────┘
```

**一天出十次包就是一小时。** 所以在电脑桌面能验证完的，一律不要等包：

| 改动类型 | 在哪验 | 耗时 |
|---|---|---|
| 界面、间距、配色、两套主题 | 浏览器里的 Web 原型（改一行 HTML 就看到） | 即时 |
| 检测阈值、防碎参数、算法行为 | 本机 Python 预演脚本（真实素材跑一遍） | 约 10 秒 |
| 触控手感、全屏观感、iphone 上的可读性 | 原型加到 iPhone 主屏 | 即时 |
| **相册读写、导出、4K 性能、草稿恢复** | **必须真机** | 5 分钟一轮 |

**只有最后一行才值得出一包。** 记住这个，能省下大量时间。

---

## 二、真机循环的五步（照着做）

```bash
# 1. 改代码
git add . && git commit -m "xxx" && git push

# 2. 版本号 +1（忘了这一步，手机会装不上或装完还是老的）
#    建议做成脚本自动自增，别手改

# 3. 云构建 + 自动签名 → 拿到ipa（Codemagic 勾 automatic signing 最省事）

# 4. 传到你的服务器 /bk/ 覆盖旧 ipa
scp BKClip.ipa root@49.233.219.150:/bk/bkclip.ipa

# 5. 手机 Safari 打开固定链接，点一次安装
#    https://你的域名/bk/index.html
```

**链接地址必须固定**（一直是 `/bk/index.html`）。每次只换背后的 ipa —— 这样你手机书签存一次永久有效，不用每周找新链接。

**第 2 步是最容易忘的**，而且症状具有迷惑性（装到一半失败、或者装完发现还是老样子）。已经写成脚本的话就永远不会漏。

## 三、没有 Xcode 控制台，你的三件debug武器

看不到实时 NSLog，这是无 Mac 开发最大的痛点。替代方案：

### 武器 1 · App 内调试面板（主要手段）

`app/DebugConsole.swift` 已经交付。**连点版本号 7 次唤出**。

它的价值在今天才能真正体现 —— **写代码的时候就要为它服务**：

- 关键分支都打点（见《埋点规范》第 01 章），这里看的不是 Bug，而是**每一步的中间结果**
- 尤其注意：自动检测要同时记 Otsu 原始值和夹逼后的值；导出失败要带上当时的分辨率和码率
- 底部那个**实时内存读数**最重要 —— 视频 App 最可能的死因就是内存峰值被系统杀，有读数一眼确认，不用猜

日志能一键导出文件，你直接发我，我就能还原现场。

### 武器 2 · 崩溃日志 `.ips`

路径：iPhone 设置 › 隐私与安全性 › 分析与改进 › 分析数据
找 `BKClip-日期.ips`（文件名带 App 名），airdrop 或导出给我。

**App 一打开就闪退这类问题，只能靠它查** —— 面板看不到崩溃。两者互补。

### 武器 3 · 肉眼 + 录屏

不要轻视这一条。**手势跟不跟手、动画卡不卡、导出方向对不对**，都只有肉眼能判断。iPhone 自带录屏（控制中心加一下），录一段发我比描述半天管用。

## 四、⚠ 一条必须在第一版就验证的业务风险：剪映兼容性

这条单独拎出来，因为它关系到的不是「功能好坏」，而是**这个 App 有没有存在价值**。

你的实际工作流是：

```
手机拍 → 【本 App 去气口】→ 导入剪映继续剪辑 → 发布
```

**如果导出的 mp4 剪映读不出来（或者能读但音画不同步），那么中间这一步做得再好，整条流水线也是断的。**

所以第一版出包，**必须在真机上做这一项**：

1. 导出一条 → 相册里确认能打开、**方向是竖的**
2. **发到微信/存到文件夹，用剪映导入** → 确认能读、音画同步、时长正确
3. 再试一次：把导出的片子**再放回本 App 读一遍**（二次编辑的闭环）

第 1 步的「方向」是刚踩过坑的地方；**第 2 步的剪映兼容还没验证过，这是目前最大的未知项**。

建议在Python 预演阶段就顺手验一下 —— 现在 `tools/` 里那两个导出的 mp4（`IMG_2969_去气口试听.mp4`、`IMG_2981_去气口试听.mp4`）就是标准 MP4/H.264/AAC，**你现在就可以先拿它们试一遍导入剪映**，看看通不通。

如果那两个文件剪映能正常打开，就说明这套导出规格是对的，Swift 端照抄即可。**这个验证今天就能做，不用等 App。**

## 五、第一版必测清单（按风险排序）

| # | 测什么 | 不做会怎样 |
|---|---|---|
| 1 | 相册授权弹窗 → 导入一条 1080p60 竖屏 | 读不到素材，全盘皆输 |
| 2 | 波形正常出、自动检测给出合理阈值 | 核心功能 |
| 3 | **导出 → 方向是竖的 → 剪映能读** | 见上一节，**最高优先级** |
| 4 | 点红/绿反转、拖边缘微调 | 核心交互 |
| 5 | 双指缩放 + 拖动 + 指针居中 | 核心交互 |
| 6 | 深浅两套主题 | 已定的需求 |
| 7 | 切后台再回来，草稿还在 | 第 02 章的验证 |
| 8 | **上滑杀掉 App，重开还在编辑同一条** | 同上，这是最容易翻车的 |
| 9 | 连续导出 3 条，看有没有崩 | 内存/句柄泄漏 |

第 8 条要专门说：**上滑强杀是唯一测「自动保存」是否真的工作的方法**，别的测法都不算数（正常切后台是骗不了人的）。

## 六、提速技巧（攒批，别一次一包）

1. **攒批出包**：不要改一个按钮出一包。把几处改动攒一起，一轮验完。
2. **能在 UI 上调的就不要写死**：阈值、防碎参数如果在设置页可调（哪怕是隐藏入口），调参就不用重出包了。这在第 02 章的数据结构里已经预留了字段。
3. **版本号自增脚本化**、链接固定化 —— 消除低级错误。
4. **先用 Web 原型把界面调顺**，再写 Swift。写在 Swift 里的界面调整，每次验证 5 分钟；写在 HTML 里的，5 秒钟。

## 七、故障速查表

| 现象 | 最可能的原因 | 怎么确认 |
|---|---|---|
| 点了安装链接**毫无反应** | Nginx MIME 没配 / 用了 http / 证书不受信 | 电脑浏览器直接访问那个 plist，看能不能下载；必须是 https |
| 装到一半**提示失败** | UDID 没加到设备列表，或 profile 里没勾这台 | Developer 后台核对设备清单 |
| 装完**打不开** | 开发者模式没开 / 没信任开发者 | 设置里两个一次性开关（只头一回需要） |
| 装完**还是老样子** | **版本号没自增** | 设置页看版本号对不对 |
| **一点就闪退** | Info.plist 缺权限描述（相册） | `.ips` 日志会明说缺哪个 key |
| 素材**读不出来** | 相册权限被拒，或用了会失效的文件 URL | 确认草稿里存的是 `localIdentifier` |
| **用一会儿才崩** | 内存峰值被系统杀掉 | 调试面板看实时内存曲线 |
| **导出失败** | 参数组合触发编码器限制 / 磁盘不足 | 面板日志里的分辨率 + 码率 + 错误码 |
| 导出**完spěchy 是横的** | `writerInput.transform` 没设 | 见《导出管线》第 03 章第三节 |

## 八、给编程 AI 的约束（写代码前就说清楚）

- 每个可能失败的环节都要有**可读的错误提示**，不要静默失败
- 关键分支按《埋点规范》打点 —— **这是没有 Xcode 时唯一的信息通路**
- 阈值、防碎参数尽量做成运行时可调，别写死成常量
- `Info.plist` 里的相册权限描述（中文）必须齐全，否则一授权就崩
- 任何奇怪的行为，先假设是**编码过来锻炼**...导出方向和内存这两件事，再查别的
