## 0. 一句话定位

探店口播视频的**去气口工具**：导入一段（或多段）视频 → 自动找出「嗯、啊、停顿」并标记 → 手动微调 → 导出成品。

不是通用剪辑器。不做转场、滤镜、字幕、配乐、调速。

### 3.1 起始页：草稿网格（2026-10-02 晚定稿，参照相册式素材库）

**骨架**：顶部「草稿 (N)」计数 + 右上操作 → 「最近编辑」筛选行 → **三列封面网格**
→ 右下金色悬浮 ⊕（导入新的一批）→ 底部版本行。**不做底部 tab**（单功能工具不需要）。

#### 一个草稿 = 一次导入的**一整批**（皓哥口述，这条改了数据模型）

> 「我这次操作添加了 5 个视频，每个视频剪切口操作完成之后，导出了视频，然后关闭。
> 关闭剪辑界面草稿箱里边多了一个草稿，**这个草稿是包含刚才那 5 个视频的**。」

所以草稿不是「一个视频一条」，是**「一批一条」**：

```
导入 5 条  →  建 1 个草稿（里面装着这 5 条）
            ↓  ☰ 素材列表里能看到的就是这 5 条，逐条切、逐条导
退出编辑页 →  起始页草稿箱多出 1 格（代表这一批）
再点进去   →  5 条都还在，各自的刀口、指针位置、阈值都还在，接着改
```

**为什么这么设计**（跟他的用法严丝合缝）：一次加的多条素材本来就是**同一场景的不同口播片段**，
打包成一个草稿，回马枪的时候点一次就能回到那批现场，不用在草稿箱里翻零散的 5 条。

> ✅ **皓哥已当面确认这段叙述**（2026-10-02 23:59：「你的叙述非常好，就是这样」）。
> 上面这段就是最终口径，写代码实现时以它为准。

| 项 | 规则 |
|---|---|
| 格数 | **最多 10 个草稿**（= 10 批），超了丢最久没动过的那批 |
| 排序 | 按 `lastEditedAt` 倒序 |
| 封面 | 取**最后编辑那条素材**、上次停住的那一帧 |
| 角标 | 左下角显示这一批的**合计刀数**（金底黑字） |
| 「···」菜单 | **重命名 / 删除 / 直接导出**（皓哥定的三项） |
| 点封面 | 载入这一批，进到**上次编辑的那条** |
| 默认名 | 第一批那条素材的名字 + `等 N 条`（如 `IMG_3027 等 5 条`），可重命名 |

**整批从头到尾一刀没切 → 不留**（皓哥 2026-10-02 定）：

```
退出编辑页那一刻判定：
    这一批从头到尾动过刀（everEdited = true）  →  保留，且**永不自动删**
    从头到尾一刀没切                            →  整个草稿丢掉，不进起始页
```

> ⚠️ 判据是 **「曾经动过刀」，不是「退出时还有没有刀」**（皓哥 2026-10-03 拍板）。
> 所以：某批切过刀、后来又把刀全删干净再退出 —— **它照样留着**。
> 理由很实在：一旦入过库，用户心里就认为「它已经存下了」，再让它凭空消失会让人怀疑是不是丢了数据。
>
> 实现：草稿上挂一个 `everEdited` 布尔，任何一次 commit 让 cuts/splits 变成非空就置 true，
> **只置不清**（撤销也不清 —— 撤销是把刀撤掉，不是把「我编辑过这件事」抹掉）。
>
> 连带好处：起始页不会出现「0 刀」空草稿，角标统一是金底黑字。

> ⚠️ 存的是**草稿**（刀口数据 + 一张封面小图），**不存视频本身** —— 原片还在相册里。
> 一份草稿几百字节 + 封面约 20KB，留 10 批几乎不占空间。
>
> 「动过刀的判定」（`cuts 或 splits 非空`）现在有**三处**共用：
> 编辑页列表名字变红、批量导出的范围、**以及这个草稿退不退出**。三处同一个标准，别各写各的。

**留存的完整规则**：

```
进起始页的草稿 = 最近 10 批，且每一批都 everEdited = true
                 ↑ 从头到尾一刀没切的，退出时直接丢
                 ↑ 曾经动过刀的，永不自动删（哪怕后来把刀删干净了）
                 ↑ 超过 10 批的，丢最久没动过的
```

### 3.2 批量删 / 批量恢复（皓哥 2026-10-03 定：都做）

**入口**：起始页右上那个「批量多选」图标（参照图里就有）→ 进多选态 → 勾选封面 → 底部出操作条。

| 操作 | 行为 |
|---|---|
| **批量删** | 勾几条删几条，全部进「最近删除」 |
| **批量恢复** | 在「最近删除」里勾选，一键还原回网格 |
| 单条删 | 「···」菜单里的删除，同样进「最近删除」 |

**回收站怎么设计**（删掉的是刀口数据，删了等于白切，所以必须有退路）：

| 项 | 规则 |
|---|---|
| 删除 ≠ 销毁 | 移进「最近删除」，可以捞回来 |
| 入口 | 起始页顶部「草稿 (N)」旁边一个入口，或者「···」里 |
| 保留期 | **30 天后自动清空**（跟相册一个套路，不无限堆着） |
| 手动清空 | 「最近删除」里提供「清空」按钮，带二次确认 |
| 二次确认 | 单条删只提示「已移到最近删除」（可撤销感），**清空回收站才弹真正的确认框** |

> ⚠️ 恢复时要检查：这条草稿对应的**原视频还在不在相册里**。
> 用户可能在删掉草稿之后又把原片删了 —— 那种情况下恢复会失败，给一句人话提示，别崩。

### 4.3 预览区（画面）

**皓哥 2026-10-02 晚定稿：预览区要按素材是横版还是竖版自己变高度，但变归变，不许把下面的区域挤没了。**

比例取 `BKAssetProbe` 算出的**真实显示尺寸**（已经应用过 preferredTransform 的那个），
不许直接用 naturalSize —— 见最上面三条方向铁律第 1 条。

```
预览区高度 h = clamp( 内容宽 398 ÷ (显示宽/显示高) , 下限, 上限 )
```

| 素材 | 398 宽时算出 | 实际取 |
|---|---|---|
| 16:9 横版 | 224 | 224（矮） |
| 4:3 | 299 | 299 |
| 1:1 | 398 | 封顶 |
| 9:16 竖版 | 708 | **封顶**（画面按比例缩小、居中，两侧留黑） |

**已拍板（2026-10-02 晚）：**

- **上限 350pt**：竖版再长也不许超过它 —— 这就是皓哥说的「不许挤压下面的区域太多」
- **下限 200pt**：横版再扁也不许低于它

预览区变矮省出来的空间、**全部补给主轨道**；反过来也一样。
这样既满足「画面有上下变化」，又不会在屏幕上留一块难看的空白：

```
主轨道高度 = 170 + (310 − 预览区高度)   // 再夹到 [130, 300]
```

| 素材 | 画面高 | 主轨道高 |
|---|---|---|
| 16:9 横版 | 224 | **256** |
| 1:1 方片 | 350（封顶） | 130 |
| 9:16 竖版 | 350（封顶） | 130 |

三种比例下，**画面↔数字行↔轨道↔概览的间距恒为 16，工具栏恒为 782–882**。
这条已经用 `tools/render_layout_preview.py` 验过，改任何元素前先跑它看有没有越界。

> 画面始终保持素材原始比例（`AVLayerVideoGravity.resizeAspect`），
> 高度被夹住的时候就是左右留黑，绝不拉伸变形。

### 4.5 主轨道（关键几何）

**指针钉死在正中央不动，内容在底下左右滚。**

| 量 | 值 | 说明 |
|---|---|---|
| W | 可视宽度 | |
| pad | W/2 | 左右各留**半屏余量** |
| pps | 每秒像素数 | 由缩放决定 |
| L | duration × pps | 内容长度 |
| 画布总宽 | L + W | 内容 + 左右余量 |
| 滚动范围 | [0, L] | |
| **指针时间** | **= contentOffset / pps** | 因为 pad 恰好 = W/2，两者相消 |

> ⚠️ 余量必须取半屏，上面这条恒等式才成立。改任何一个数都要重推一遍。

- 滚动惯性和回弹交给 UIScrollView，不自己撸 pan
- 只有「拖边界把手」需要与滚动抢手势：摸到把手才临时关掉滚动
- 播放时内容持续向左滚（30fps 更新）

#### 4.5.1 拖轨道找位置：画面跟着走，但**不许出声**（皓哥 2026-10-02 晚着重强调）

| 操作 | 画面 | 声音 |
|---|---|---|
| 左右拖轨道 / 拖指针 | **实时跳帧**（跟着动） | **静音** |
| 双指捏合缩放 | 停在手指中点那一刻的画面 | 静音 |
| 点概览条跳转 | 跳到那帧 | 静音 |
| **点 ▶ 播放** | 连续播放 | **有声** |

> 一句话记牢：**只有按下播放键，才允许有声音。** 手动找位置的过程全程无声。
>
> 实现上天然成立：`AVPlayer` 只有在 `rate > 0` 时才出声，
> scrub 一律走 `seek(to:)`（此时 `rate == 0`）。**所以千万别用播放中的 player 去 seek 来模拟 scrub。**

**拖完之后停还是继续 —— 皓哥 2026-10-02 晚拍板：**

> 「手拖动轨道，松手的时候，它是停在那的。如果播放中去拖动的话，它也是会暂停播放的。」

所以规则是**一律停下来**，不存在「松手续播」这种剪映式手感：

| 场景 | 结果 |
|---|---|
| 没在播 → 拖轨道 | 画面跟着走，**松手就停在那** |
| **正在播 → 手指碰轨道** | **立刻暂停**，画面停在手指松开那一帧 |
| 松开之后想继续 | 必须再按一次 ▶（从新的指针位置起播） |

> 这条比剪映保守，但好处很实在：误碰一下不会「哗」地把声音放出来，
> 也不用去找停止键。代码上简单 —— 拖动手势一起手就 `player.pause()`，别的什么都不用做。

#### 4.5.2 播放：从橙色指针处起播，且要「按下去几乎是立刻响」

**播放永远从指针当前所指的时间开始**，不是从头，也不是从上次停的地方。

皓哥明确提了「尽量减小按下播放到出画面的延迟」。要做到这一点，靠的是**在按下之前就把活干完**：

| 手段 | 说明 |
|---|---|
| player / playerLayer **常驻** | 换素材只换 `AVPlayerItem`，绝不重建 AVPlayer。重建一次几十到几百毫秒就没了 |
| `automaticallyWaitsToMinimizeStalling = false` | 默认是 true，系统会为了不卡顿而**故意多缓冲一会儿才起播** —— 这就是延迟的大头 |
| **指针一停下就后台 preroll** | 手指离开屏幕 / 滚动减速停住的那一刻，立刻异步 `seek(精确)` + `preroll(atRate: 1)`，把这一帧预解码好。等按播放时只剩 `play()` 一步 |
| seek 用零容差 | `toleranceBefore: .zero, toleranceAfter: .zero`。精确落点，代价是略慢，但因为已经提前 preroll 过了，用户感知不到 |
| 起播路径保持极短 | 按下 ▶ 只做一件事：`player.play()`。不许在这一步里再去做 seek、重建 item、改音频会话 |
| 音频会话提前设好 | `AVAudioSession.setCategory(.playback, mode: .moviePlayback)` 早就设过了（这事儿踩过坑），**不要再在播放路径里碰它** |

> 起播后画面跟着播、波形同步往左滚；播到素材尾自动停，指针停在末尾。

**停止键取消之后，按 ■ 是停在哪？**

| 场景 | 指针去哪 |
|---|---|
| 按 ■ 停 | **停在原地**（看着哪一帧就停在哪）—— **皓哥 2026-10-02 拍板** |
| 想回到开头 | 拖轨道到最左，或点概览条最左边 |

> ⚠️ 旧版「停止 = 暂停 + 指针回到 0 秒」**已作废**。现在 ■ 就是暂停：
> 正看着某一帧按一下停，指针却弹回开头会很别扭。想重新开始自己拖回最左。

#### 4.5.3 拖到头还继续拽 → 直接换素材（皓哥 2026-10-02 晚定稿）

编辑区像一条能一直往下搓的胶卷：搓到尽头搓不动了，再一使劲就翻到隔壁那条，
不用退回列表里去点。

| 场景 | 结果 |
|---|---|
| **先拖到片头**，还继续往右拽超过 60pt 再松手 | 装载列表里的**上一条** |
| **先拖到片尾**，还继续往左拽超过 60pt 再松手 | 装载列表里的**下一条** |
| 越界不足 60pt | 只回弹，**不换** |
| 已经是第一条（或最后一条），继续往同方向拽 | **换不了，弹回片头 / 片尾**（弹到边界那一帧，不是回原处） |
| 总共只有一条素材 | 同上，只回弹 |

**换进来之后（皓哥拍板）：**

- **指针一律停在新素材的片头** —— 不管是从上一条进来的还是下一条进来的，都一样，
  都是从第 0 秒开始看。不做「顺着手指方向停在片尾」那种处理
- 缩放档位保持当前值不变
- 换之前先 `pause` + 存当前草稿（跟点 ☰ 列表里切换素材走同一套动作）

> **三个必须防的坑**（都是实际会发生的，不是理论）：
>
> 1. **加载期间加互斥锁，一次只准换一条。** 不锁的话手指使劲一划能连跳三四条，
>    每条都要重新提一次波形，直接卡死。加载没回来之前，越界判定直接短路返回
> 2. **判「越界了多少」，不判手指速度。** 慢悠悠拖过头也算数，
>    快甩一下但没过阈值也不算。用 `contentOffset.x < -60` / `> L + 60`
> 3. **它跟「拖边界把手」抢手势。** 只有在头尾两端、且没摸到气口把手时，
>    这个换素材的逻辑才生效（顺序：先判把手，再判越界）

> ❓ **待定**：第 5 节里原有的「左右滑画面换素材」跟这个是两回事
> （一个在画面区滑，一个在轨道区拖）。两条并存会不会互相干扰，皓哥还没说，
> 暂定都保留。

#### 4.5.4 联播键 `|▶|` —— 拼起来播（2026-10-02 晚定稿）

**皓哥定的名字叫「联播键」，播放方式是「拼起来播」。**

把绿区**临时接成一条**再放，全程连贯不断，等于**预演成品**。
既然目的是听「气口去干净没、接缝顺不顺」，就必须跟导出听感一致 —— 用同一份 keepRanges。

| 项 | 定稿 |
|---|---|
| 名字 | **联播键**（皓哥命名，不是"连播"） |
| 图标 | E 方案，三角夹在两条竖线中间 |
| 播什么 | 按 keepRanges 临时拼的 composition，**不落盘**，拼好直接播 |
| 接缝处理 | 跟导出一样做 15ms 淡入淡出 —— 就是来听接缝的，必须一致 |
| 声音 | 有（这是正经播放，不是 scrub） |
| 播完 | 自动停，界面回到静止 |

**指针怎么走（实现的关键点）**：主轨道画的是**原片时间轴**，但联播放的是成品，
两边长度不一样、对不上。所以播放中要反查：

```
成品时间 → 查它落在哪个 keep 段里 → 加上该段在原片的起点 → 得到原片时间 → 更新指针
```

视觉上就是：指针在轨道上一路往前走，遇到红区就「跨」过去一小段。
这样**画面是连贯的、指针又始终对得上轨道**，两边不脱节。

> 实现提示：用 `AVMutableComposition` 按 keepRanges 插片段，生成临时 `AVPlayerItem` 播放；
> 别走「导出成文件再播」那条路 —— 又慢又占空间，还多一份临时垃圾要清理。

#### 4.5.5 两个播放键的起点逻辑（皓哥 2026-10-02 晚口述，已确认）

**两个键的起点是同一个 —— 橙色指针当前所在的那一帧。** 区别只在于联播会跳过红区。

| 按下 | 从哪儿开始 |
|---|---|
| **▶ 播放** | 橙指针那一帧，往前一路播，**红区绿区都播**（原片原样） |
| **`\|▶\|` 联播** | 橙指针那一帧；**但起点落在红区里就往下跳到第一个绿区再开始**，落在绿区就直接从那儿播；播的过程中一路跳过红区 |

**「接着听」的完整流程**（皓哥举的例子，也是这个逻辑最主要的用法）：

```
① 按 ▶ 从指针处播
② 按 ■ 停  →  指针停在原地（绿区某处）
③ 按 |▶|   →  从指针这儿接着往下联播（红区自动跳过）
```

因为停止时指针是停在原地的，所以 ▶ 停在哪、联播就从哪儿接上，中间不断档。
反过来也一样：联播听到一半停下来，再按 ▶ 就是从当前指针处按原片播下去。

> 起点落在红区时「跳到下一个绿区」—— 这个跳转是**瞬间的**，
> 界面上会看到指针往右挪一小段然后开始播，不是慢慢滑过去。

**互斥规则**：任何时候只有一个在播；按当前正在播的那个键 = 停止，按另一个 = 切换过去。

### 4.6 概览条

整条素材的缩略全览 + 橙色视窗框（标明你现在看的是哪一段）。点它任意位置直接跳过去。

补充：气口区间在概览条上也用粉红块画出（60% 透明）。定稿原文只写了「灰底小波形 + 橙色视窗框」，
但概览条上不标气口的话，就看不出「前面还有几刀没处理」，这条信息缺失会让概览条只剩导航价值。

### 4.7 数字行 + 底部两行

**数字行（紧贴画面预览区下面，皓哥 2026-10-02 定）**

```
00:12 / 00:42          原 00:42 · 剪后 00:38 · 7 刀 · 删 3.2s（7.6%）
```

- 左：`当前时间 / 总时长`，跟随指针跳动，15pt 等宽加粗
- 右：`原时长 · 剪后时长 · 刀数 · 删了多少（占比）`，11pt 次要灰，右对齐，最多两行
- 这一整行只放数字，不放提示语 —— 提示语在底部状态行

**底部两行**

- 阈值滑杆：调灵敏度，松手 0.4 秒后重算
- 状态行：`正在提取波形…` / `导出中 42%` / `已撤销` / `这里已经有一道切口了` 这类瞬时提示

#### 4.7.1 阈值的「恢复自动」按钮（皓哥 2026-10-03 定：做）

**问题**：进一条素材时 Otsu 会**自动**算一个阈值；你一拖滑杆它就变成**手动值**了。
拖乱之后想回到自动算的那个值，原来只能退出重进，或者凭手感拖回去。

**做法**：阈值滑杆右边加一个小图标按钮（圆弧箭头，就是「回到自动」的意思）。

| 状态 | 按钮 |
|---|---|
| 当前就是自动值（没手动拖过） | **置灰**，点了没反应 |
| 手动拖过 | 亮起，按一下 → 回到 Otsu 自动值 → 顺带重算气口 |

> 它救的是「拖乱了回不去」这种真会发生的场景，成本就一个小图标 + 一行代码。
> 而且有了这个锚点，你拖阈值微调时会更敢下手 —— 反正回得去。

### 4.8 导出（皓哥 2026-10-02 晚定稿：要能一次导出一批）

点导航栏那个「导出」→ **先选范围**，再开始：

| 选项 | 行为 |
|---|---|
| **只导出本段** | 导出当前这一条 |
| **导出全部（改过的）** | 列表里**所有动过刀的**素材，逐个各导出一条 |

> **为什么要有批量导出**（皓哥的理由）：
> 「一次加入多个视频，这都是在同一个场景的不同的口播片段。处理完之后一键全部导出，
> 这批视频就都进剪映了。」
>
> 「改过的」= `cuts 或 splits 非空` —— 跟列表里名字变红、草稿列表判定用的是**同一条**。
> 一刀没切的素材不导出（导出来等于原片，白占相册空间）。

**文件命名**（皓哥定）：原文件名前面加 `BK_`，同一条导出多次再加后缀区分。

| 这条素材第几次导出 | 相册里的名字 |
|---|---|
| 第 1 次 | `BK_1.mov` |
| 第 2 次 | `BK_1_1.mov` |
| 第 3 次 | `BK_1_2.mov` |

```
第 k+1 次导出时：k = 这条素材已导出的次数
    k == 0  →  BK_{原名}        （第 1 次，不加后缀）
    k >= 1  →  BK_{原名}_{k}    （第 2 次 _1，第 3 次 _2，往后顺推）
```

序号直接读 `exportHistory.count`，不用另外记账。
**规律已确认**：第 1 次不加、第 2 次 `_1`、第 3 次 `_2`，之后 `_3`、`_4` 顺推（皓哥 2026-10-02 拍板）。

> 为什么要后缀：同一条片子改一版导一次，剪映里就会躺着好几版，
> 名字一模一样根本分不出哪版是哪版。

**批量导出时**：逐条排队处理，状态行显示 `正在导出 3/8 …`；
单条失败把它记下来继续跑完剩下的，最后统一报一句「7 条成功，1 条失败」，
不要中途弹窗把整批打断。

### 4.9 导出设置（皓哥 2026-10-03 定：规格要有得选）

**分辨率、帧率都要有可选项，默认跟源视频一样。**

| 设置 | 可选项 | 默认 |
|---|---|---|
| **分辨率** | **同源文件 / 1080P**（就这两个） | **同源文件** |
| **帧率** | **同源文件 / 60 / 30**（就这三个） | **同源文件** |

放置位置：点「导出全部」之后，面板里多一行设置区（两个下拉），选完再开始。
默认都是「同源文件」，所以日常一键导出不用碰它。

> 选项刻意做少：分辨率砍掉了 720P / 480P，帧率砍掉了 24。
> 探店素材就 1080P 竖版这一种，多一个选项就多一份要维护、要测试的参数组合。

**容器与编码不变**（这几个是剪映实测过的，别动）：MP4 / H.264 / yuv420p / AAC-LC 192k / faststart。
可选项只放开**分辨率**和**帧率**这两项。

#### 4.9.1 一批里各条参数不一样时，全部导出按谁？（皓哥定）

> 「同一批导入的视频参数不同，则全部导出时按**时长最长的那个视频**的参数导出。」

```
优先级：
  ① 用户手动选了分辨率/帧率   →  用手动值，全批统一
  ② 用户选「同源文件」        →  单条导出用各自的；
                                  批量导出用【时长最长那条】的参数，全批统一
```

举例：一批三条，A 是 1080P/60fps（15 秒）、B 是 1080P/30fps（42 秒，**最长**）、C 是 720P/30fps（8 秒）
→ 全批统一按 **B 的参数：1080P / 30fps** 导出。

> ⚠️ 这样会把 C 从 720P **拉到** 1080P（放大，画质不会变好，文件变大）。
> 这是视频剪辑软件的常规做法（导出设置统一应用），不做特殊处理，
> 但状态行要如实显示实际输出规格，别让人以为文件变大了是出错了。

#### 4.9.2 改分辨率时的旋转处理（别踩坑）

分辨率选项作用于**显示尺寸**（已应用 `preferredTransform` 之后那个），不是 `naturalSize`。

```
目标显示尺寸：竖版 1080P = 1080 × 1920（长边是高度）
写入宽高    ：把显示尺寸按 transform 反方向转回去
              竖版 1080P 的素材，naturalSize 存的是 1920×1080 横着放的
              → 写入时给 1920×1080，transform 仍设 preferredTransform
```

> 一句话：**分辨率变了，写入的宽高要跟着变，但 transform 永远是源素材那个 preferredTransform**。
> 漏了 transform 成品必躺下 —— 这是项目里排在第一梯队的老坑，改分辨率时尤其容易忘。

### 4.10 ⚠️ 视频方向：五个环节都要检查（皓哥 2026-10-03 特别叮嘱）

> 「一定注意选择视频后，进入预览区，视频的旋转方向不要出错。」

iPhone 拍的视频永远是**「横着存 1920×1080 + rotation -90 标记」**，真正看是 **1080×1920 竖版**。
这个"存的"和"看的"是两回事，五个环节每个都可能踩：

| # | 环节 | 正确的做法 | 踩了会怎样 |
|---|---|---|---|
| ① | **选完视频进预览区** | 画面高度用**显示尺寸**（1080×1920）算比例，播放器用 `resizeAspect` | 画面被压扁，或者预览区高度算错挤到下面 |
| ② | **起始页草稿封面** | 抽帧后按**显示尺寸**裁，竖版就裁成竖的一张 | 封面躺着，网格里看着很怪 |
| ③ | **导出写入** | 宽高给 **naturalSize 方向**（未旋转的 1920×1080），`transform = preferredTransform` | **成品躺下**——老坑一号 |
| ④ | **导出成品容器** | 保留 rotation 标记（ffmpeg 侧 `-noautorotate`） | 标记丢了，或者被转两次 |
| ⑤ | **相册 / 剪映里看成品** | 应该显示成 1080×1920 竖版 | 导入剪映变成横的 |

**实测证据**（2026-10-03，四条样片跑通，见 `samples/`）：

```
源片  IMG_4580 : 1920x1080 + rotation -90
成品           : 1920x1080 + rotation -90     ← 一致，方向没躺
（4582 / 4583 / 4990 三条同样一致）
```

> 以后每次改导出参数（尤其是分辨率），都要重跑一遍这个对照。
> 一句话口诀：**存的横着，看的竖着，transform 一次都不能少。**

## 7. 数据模型要点

- **切开 ≠ 删除**：`splits` 不进 `cutRanges`，导出时长不受影响
- 删除区间必须走 `BKTimeline.build`（内含 `merge`，会合并重叠）
- 拖动边界按**时间**找，不按 index（index 会随显示粒度变）

### 7.2 草稿与导出的记账（2026-10-02 晚补）

| 数据 | 规则 |
|---|---|
| **结构** | **两层**：草稿（一批）→ 素材项（多条）。别再按「一视频一草稿」存 |
| 草稿层 | `assets[]` 素材列表、`lastEditedAt`、`lastAssetId`（上次在改哪条，封面和重进都靠它）、`title` |
| 素材项层 | `assetId`（相册标识）、`name`、`cuts`、`splits`、`threshold`、`playheadTime`、`exportCount` |
| 草稿留存 | **最多 10 批**，按 `lastEditedAt` 倒序，超了丢最老那批；**整批一刀没切的，退出时直接丢**（3.1） |
| `exportCount` | 挂在**素材项**上（不是草稿）—— 导出文件名的后缀序号靠它，每条素材各记各的 |
| `exportHistory` | 起始页「已导出 N 条」的累计计数 |
| `everEdited` | 挂在**草稿**上：任何一次编辑让它变成非空就置 true，**只置不清**（撤销也不清）。草稿留存的判据，见 3.1 |
| 回收站 | 删除的草稿移进「最近删除」，30 天后自动清空；恢复时要先确认原视频还在相册里 |
| 动过刀的判定 | `cuts 或 splits 非空`，**三处共用**：编辑页列表名字变红、批量导出的范围、草稿退不退出。别各写各的 |

### 7.1 撤销 / 重做（2026-10-02 补）

- 撤销单位是**整个工程快照**（项目是值类型，一份才几百字节），
  不做「操作 + 逆操作」—— 两个气口重叠被 merge 之后逆不回原来的两条
- **一次拖动只占一格**：第一帧 `push`，之后全部 `amend`。
  反过来（先 amend）会把「拖动前的状态」覆盖掉，那一步就永远撤不回来了

**容量（皓哥 2026-10-02 晚拍板，改掉了原来的 60）：**

| 栈 | 容量 |
|---|---|
| **撤销** | **最多 15 步** |
| **重做** | **最多 1 步** |

```
新操作到来  →  压进撤销栈（超 15 丢最老的），同时**清空重做栈**
撤销一次    →  从撤销栈弹出，压进重做栈（重做栈超过 1 就丢最老的）
重做一次    →  从重做栈弹出，压回撤销栈
```

> 重做只留 1 步意味着：**连着撤销两步之后，先撤的那一步就救不回来了**
> （重做栈里只剩最近撤掉的那步）。这是皓哥明确要的效果 —— 撤销能退得深，
> 但重做只保底下那一步，防止来来回回撤了又做、做了又撤把状态搅乱。
>
> ⚠️ 逻辑先在 `tools/verify_history_stack.py` 里跑随机用例验证过再改 `BKHistory.swift`，
> 别直接上手写 Swift。改容量时两边一起改。
