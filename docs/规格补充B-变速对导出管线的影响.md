## 1. 被打破的核心假设

导出方案原文（`docs/v2.0技术方案-折叠与多轨导出.md` §数据模型）：

> `BKMark`(keep/cut) + `splits` + `keptRanges`（记录B）；
> **轨道时间轴 = 原片时间，duration 不变，零换算**

以及 §坐标系：

| 坐标 | 范围 | 定义 |
|---|---|---|
| **源时间 (src)** | `0 ~ duration` | 永远不变，**所有标记的存储坐标系** |
| **输出时间 (out)** | `0 ~ displayDuration`<br>= `duration − Σ 折叠长度` | 播放/导出成品的坐标系 |

**变速打破的是「零换算」**：一旦 `speed ≠ 1`，`src → out` 不再是"减去折叠长度"，
还要叠加"**按倍速缩放**"。原方案的换算函数 `out(u) = u + Σ 折叠长度` **不再成立**。

---

## 2. 具体影响面

### 2.1 时间轴不再等于时间

| 项 | 变速前 | 变速后 |
|---|---|---|
| 区块 `a/b`（轨道坐标） | = 源片时间 | **≠ 源片时间**（已按倍速缩放） |
| 折叠线位置 | 源片秒 | 缩放后需回映射到源片秒 |
| `duration` | 源片时长 | `baseDuration / speed` |
| `TOTAL` | Σ 区块时长 | 随变速实时变（原型已实现） |

> 原型里 `baseDuration` 锁存 `speed=1` 时的时长，正是为了能反算回源片时间。
> **编程侧必须保留这个字段**，否则无法把缩放后的轨道坐标还原成 src 坐标。

### 2.2 必须新增的换算层

```
当前：out(u) = u + Σ(折叠线输出位置 ≤ u 对应折叠长度)

变速后需三层：
  1. 轨道坐标 → 源片坐标：  src = trackT * speed        （speed 为该区块倍速）
     ⚠️ 不同区块倍速可能不同 → 需按区块分别换算，不能全局乘一个系数
  2. 源片坐标 → 输出坐标：  out = src + Σ 折叠长度       （原方案逻辑不变）
  3. 导出取样：            按 out 区间取 src 区间
```

**★ 关键风险**：`speed` 是**逐片段**的。若 4 个区块分别是 1x/2x/0.5x/1x，
`trackT → src` 就**不是单一乘数**，换算必须**逐区块查表**。
原型 `applySpeed` 的"应用到全部"会拉平所有倍速，真实使用中用户会逐段调 —— 必须支持混合倍速。

### 2.3 导出实测约束（会真的报错）

| 约束 | 变速后的影响 |
|---|---|
| `|tmpVideo.duration − tmpAudio.duration| ≤ 1 帧 + 余量` | **高风险**。视频按 `speed` 缩放、音频不变时，两者时长必然不等 → 需**分别按倍速重采样**，不能只处理一边 |
| 音视频同步 | 变速段必须 `AVMutableComposition` 配 `scaleTimeRange`，且**音频也要同步拉伸**（变调 vs 保持音高需拍板） |
| P2 导出方案 | **必须预留 `speed` 字段与缩放路径**，否则 P2 开工时要回头改数据模型 |

### 2.4 折叠模型交互

折叠是"把区间塌成一点"，变速后折叠点也在缩放坐标系里。
`out(0)==0` / `out(duration)==displayDuration` 等不变式**需重新定义 duration 的含义**：
是源片时长，还是缩放后时长？  建议**显式区分 `srcDuration` 与 `timelineDuration`**，别复用同一字段。

## 2.5 ⚠️ 勘误（实测，待 P2 确认）

`tools/verify_speed_map.py` 5000 轮 fuzz 实测发现：§2.2 第 2 层 `out = src + Σ 折叠长度`
在引入 `speed` 后**不再自洽**：

- 该式使每个块的 out 长度 = 绿区源长 `L`，**与 speed 无关**；
- 但 §2.1 已明确块的轨道时长 = `baseDuration / speed = L / sp`（speed 越大块越短）。
- ⇒ 同一块在编辑轨占 `L/sp`、在导出占 `L`，跨倍速块边界处播放速率错位，违反「编辑器时间轴 = 导出成品」。

**建议修正（已纳入验证脚本并全绿）**：令 **out 轴 == trackT 轴**（两轴合一，都是"折叠后的播放时长"），speed 同时压缩两者：

```
local = trackT - T_i
src   = s0 + local * sp_i        # 逐区块倍速采样源
out   = T_i + local  (== trackT) # out 与 trackT 同一轴
块播放时长 = (e0 - s0) / sp_i
```

这样 `out(0)=0`、`out(total)=Σ L/sp`、跨倍速块边界连续，且 `baseDuration=L` 与 §2.1 一致。
**待 P2 拍板**：确认采用「out==trackT（speed 压缩输出）」而非「out 取源长之和（speed 只改轨宽）」。
前者为通用剪辑软件（剪映 / PR）行为，推荐采用。

## 3. 建议的落点与顺序

### 3.1 立刻可做（不阻塞 UI）
- `Region` / `pipItem` 增加 `baseDuration: Double?`（speed=1 时的时长）与 `speed: Double`
- 文档里**现在就把 `srcDuration` / `timelineDuration` 两个概念定死**，别等实现时再想

### 3.2 变速 UI 落地时必须同步交底的产出
1. 轨道坐标 ↔ 源片坐标的**逐区块换表**（不要全局乘数）
2. 音频处理方案：**变调 / 保持音高** 二选一（建议保持音高，剪辑场景更常用）
3. 导出取样时视频/音频**分别缩放**的时序方案

### 3.3 验证方法（沿用既有做法）

`docs/v2.0技术方案-折叠与多轨导出.md` 已定下"**先 Python 复刻跑通再落 Swift**"的路子，
变速沿用同一套：

1. **新建 `tools/verify_speed_map.py`**（方案里引用的 `verify_fold_map.py` 也还没建，可一并做）
   - 随机生成混合倍速场景（各区块 speed 随机取档位）
   - 验证 `trackT → src → out → trackT` 往返一致，误差 < 1e-6
   - 验证 `out(0)==0`、`out(timelineEnd)==timelineDuration`
   - 验证折叠点在缩放坐标系下仍塌成一点
2. 造脏数据：倍速 0.1x 与 4x 极端组合、连续同倍速、相邻不同倍速
3. 全绿后再写 Swift，**别直接改 Swift 试**

### 5.1 duration 字段权衡（已定：A）

| 维度 | A. 拆 srcDuration/timelineDuration（**已采用**） | B. 保留单 duration + speed |
|---|---|---|
| 实现成本 | 略高：模型多一字段，所有读 duration 处需分清用哪轴 | 最低：只加一个 speed 字段 |
| 出错率 | **低**：语义显式，编译器/审查可查混用 | **高**：每处都得心里记"这是源轴，轨道时长=÷speed" |
| 效率 | 无差别（多存一个 Double） | 无差别 |
| 风险 | 低 | 预览/导出/轨道宽/相册 metadata 任一处漏算即错位——**正是本次 speed 验证抓到 bug 的温床** |

**已定：A**。长期返工成本最低，且与 §2.4 建议一致。
