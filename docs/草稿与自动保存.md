# 草稿与自动保存（完整开发文档 · 第 02 章）

## 一、先分清三件事

| | 管什么 | 存在哪 | 关 App 后 |
|---|---|---|---|
| **撤销栈** | 回到上一步 | 内存 | 消失（已定稿：命令模式，50 步） |
| **自动保存** | 下次打开接着编 | 磁盘 | 保留 ← 本章要做 |
| **历史版本** | 回到昨天的样子 | 磁盘 | 保留 |

**结论：做前两个，第三个先不做。**

第三个不做的理由：撤销栈（50 步）+ 自动保存已经覆盖绝大多数场景。多版本快照在这个「单视频预处理器」里几乎用不上 —— 你不会想去回滚今天上午改的气口。但它会让每次保存变成写放大，还要多一套版本选择 UI。

**如果将来真想要历史感，做「导出历史」比「编辑历史」有用得多**：记录每个视频导出过几次、文件名、时间、参数。这才是对工作流有帮助的东西。

---

## 二、什么是「草稿」

**一个视频 = 一条草稿。** 这正好就是之前定的「三道线视频列表」里的那些条目 —— 现在把它们从内存态改成磁盘持久化即可，**不需要新增任何 UI**。

顺带解决的另一个问题：之前定的「编辑过气口的视频」才进批量导出队列，这个 `edited` 标记天然属于草稿数据。

**草稿不包含波形。** 波形是缓存，启动时重算（几秒）。草稿只存「重算不出来的东西」——也就是你的编辑成果。

---

## 三、数据结构

存在 `Application Support/drafts/` 下，**每条草稿一个 JSON 文件**，外加一个 `index.json` 存列表顺序。

为什么要分文件而不是一个大 JSON：单个大文件一旦写坏，全部草稿一起丢；分文件最坏只丢一条。

```json
{
  "schemaVersion": 1,
  "id": "E6A1B2C4-...",
  "assetLocalId": "A5F2.../L0/001",
  "fileName": "IMG_0231.MOV",
  "durationSec": 214.5,
  "displayW": 1920, "displayH": 1080,
  "segments": [
    { "startSec": 0.0,  "endSec": 12.4, "kept": true },
    { "startSec": 12.4, "endSec": 13.1, "kept": false }
  ],
  "thresholdDb": -37.2,
  "thresholdIsAuto": true,
  "playheadSec": 45.2,
  "viewport": { "startSec": 40.0, "pointsPerSecond": 30.0 },
  "edited": true,
  "createdAt": 772345200.0,
  "updatedAt": 772349000.0
}
```

整个文件不到 1KB。这就是为什么保存可以很激进。

### 相册引用必须用 localIdentifier（坑）

**绝对不要把相册文件的 URL 存进草稿。** 那个 URL 在相册整理、iCloud 同步、系统升级之后就可能失效，而且里面带设备 UUID（隐私）。

正确做法：

```swift
// 保存时
draft.assetLocalId = phAsset.localIdentifier

// 启动时取回
let result = PHAsset.fetchAssets(withLocalIdentifiers: [draft.assetLocalId], options: nil)
guard let asset = result.firstObject else {
    draft.isSourceMissing = true          // 不能崩，标记出来
    BKLog.shared.w("源视频已丢失 \(draft.fileName)")
    return
}
```

**取不回来时必须能优雅处理**：列表里这条变灰，标注「源视频已删除」，给删除入口。用户从相册删掉原视频是很常见的事，App 不能因此崩或者卡在加载上。

## 四、自动保存策略

四个触发条件，缺一不可：

| 触发 | 行为 | 作用 |
|---|---|---|
| 编辑后停手 | 等 **2 秒**没新操作才写（防抖） | 连续多次改动合并成一次写 |
| 停手后已满 **10 秒** | 强制补写一次（限流） | 最坏情况也只丢 10 秒 |
| 关键操作完成 | 立即写 | 自动切分、删除整段 —— 用户可能马上就退出 |
| App 进后台 / 失活 | 立即写全部 | 唯一可靠的退出信号 |

**「关闭时保存」这个概念在 iOS 上不成立。** 见下一节。

### 实现骨架

```swift
final class DraftStore {

    static let shared = DraftStore()
    private let queue = DispatchQueue(label: "bk.draft", qos: .utility)
    private let encoder = JSONEncoder()
    private var debounceItem: DispatchWorkItem?
    private var lastWriteAt = Date()
    private var dirty: Set<UUID> = []

    private let debounceSec = 2.0     // 停手后多久写
    private let maxWaitSec  = 10.0    // 最长容忍多久不写

    /// 任何编辑操作的末尾调一下
    func markDirty(_ id: UUID) {
        dirty.insert(id)
        debounceItem?.cancel()
        let item = DispatchWorkItem { [weak self] in self?.flush(id) }
        debounceItem = item
        queue.asyncAfter(deadline: .now() + debounceSec, execute: item)

        if Date().timeIntervalSince(lastWriteAt) >= maxWaitSec {
            queue.async { [weak self] in self?.flush(id) }
        }
    }

    /// 进后台、退出编辑界面、关键操作后调用
    func saveAllDirty() {
        dirty.forEach { flush($0) }
    }

    private func flush(_ id: UUID) {
        guard let draft = drafts[id] else { return }
        let url = fileURL(for: id)
        do {
            let data = try encoder.encode(draft)
            // .atomic = 先写临时文件再 rename，写一半断电不会留下坏 JSON
            try data.write(to: url, options: .atomic)
            dirty.remove(id)
            lastWriteAt = Date()
            BKLog.shared.d("草稿已存 \(draft.fileName) 切点 \(draft.segments.count) 段")
        } catch {
            BKLog.shared.e("草稿保存失败 \(error)")
        }
    }
}
```

**两个关键点：**

1. `.atomic` 必须加 —— 它让系统「先写临时文件再原子替换」。写到一半被杀，磁盘上留下的是旧的完整文件，而不是半个坏 JSON。
2. 全部写入都走同一个**串行队列**，避免并发写同一个文件。

## 五、生命周期：iOS 没有「关闭」事件

**用户上滑强杀 App 时，一个回调都不会给。** `applicationWillTerminate` 不保证被调用（官方明确说的）。所以：

- ❌ 指望「关闭时保存」= 必丢数据
- ✅ 真正的防线是「停手 2 秒就写」

能拿到回调的时机只有这几个，要在正确的委托里做：

```swift
// SceneDelegate（iOS 13+，现在的项目都是这个，不是 AppDelegate）
func sceneDidEnterBackground(_ scene: UIScene) {
    DraftStore.shared.saveAllDirty()
}

func sceneWillResignActive(_ scene: UIScene) {   // 下拉通知、来电、锁屏
    DraftStore.shared.saveAllDirty()
}
```

如果用的是 SwiftUI App 生命周期：

```swift
@Environment(\.scenePhase) var phase
.onChange(of: phase) { newPhase in
    if newPhase != .active { DraftStore.shared.saveAllDirty() }
}
```

**额外保险**：进后台时系统只给约 5 秒，一般够写，但可以申请延长：

```swift
var task: UIBackgroundTaskIdentifier = .invalid
task = UIApplication.shared.beginBackgroundTask { UIApplication.shared.endBackgroundTask(task) }
DraftStore.shared.saveAllDirty()
UIApplication.shared.endBackgroundTask(task)
```

## 六、启动时：损坏处理

启动时逐条读取，**任何一条解析失败都不能让 App 崩**：

1. 解析失败 → 把该文件改名 `.corrupt` 留着排查，跳过它加载
2. 记一条 error 日志，带文件名
3. 其余草稿正常加载

宁可丢一条，不能整个打不开。用户对「打不开」的容忍度是零。

## 七、UI 上的变化

已有的三道线列表现在变成**草稿列表**，每行增加：

- 「源视频已删除」的灰显态（点它删草稿）
- 导出过的标记（配合将来的导出历史）
- 按 `updatedAt` 倒序，最近编辑的在上面

删除草稿 = 删除 JSON 文件 + 它的波形缓存。**不删相册里的原视频**，这点要在确认弹窗里写清楚，防止用户吓一跳。

## 八、重开后恢复到什么程度

皓哥要的就是这句：**这次退出正在剪哪条、切到第几段、指针停在哪、放多大，下次打开统统还在。** 效果上跟「关闭时保存」没有差别，只是数据早在编辑过程中就已经落盘了。

| 退出时的样子 | 重开后 |
|---|---|
| 正在编辑哪条视频 | ✓ 自动回到这一条 |
| 切好的段 · 红绿区 | ✓ 一模一样 |
| 检测阈值 | ✓ 保留，含「自动 / 手动」标记 |
| 指针停在第几秒 | ✓ 停在同一秒 |
| 双指缩放倍数 · 视窗位置 | ✓ 连放大倍数都保留 |
| 波形图 | ⟳ 重算，几秒钟（它是缓存，不进草稿） |
| 正在播放 | ✗ 停在暂停态，不会自己播（符合直觉） |
| 导了一半没导完 | ✗ 不接半成品，重来一次 |
| 撤销栈（50 步） | ✗ 清空，重开只能往后撤 |

**最后一行其实是虚惊一场。** 因为咱们从一开始就定：「删除」= 把片段**标成红色**，而不是真删帧。所以重开之后虽然不能往回撤，但那段内容从来没真的消失过 —— 找到它点一下反转回绿色就回来了。

当初那个设计决策在这里派上了用场。这也是「用标记代替删除」比直接删帧强的地方。

## 九、启动行为

三种情况：

1. **有草稿** → 直接回到上次活跃的那一套（语境恢复），顶部左上角保留返回草稿列表的入口
2. **有草稿但源视频已被删除** → 列表照常显示，该条灰显「源视频已删除」，自动跳过它去选下一条可用的
3. **一个草稿都没有** → 空态，一个「导入视频」按钮，不要显示空白列表吓人

补充一条体验细节：恢复时可以显示一行极短的状态提示（比如顶部一闪而过的「继续编辑 IMG_0231」），让用户知道自己是接着上次，**不是必须的**，看你觉得有没有必要。
